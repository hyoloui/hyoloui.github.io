가상자산 추세추종 봇은 7월부터 매일 모의거래로 돌고 있다. 실제 돈을 넣기 전에 통과할 운영 관문을 G0부터 G8까지 미리 적어 뒀고, 그중 G5가 안전장치다. 자본 상한, 일일 손실 정지, 긴급 정지를 각각 강제로 한 번씩 발동시켜 확인하는 것이 기준이다.

<!--truncate-->

## 9월 23일 점검: 하나만 통과

| 장치 | 시험 | 판정 |
|---|---|---|
| 손실 자동 정지 | 가상 자산 1,000만 원에 −5%와 −20% 손실을 주입 | 통과 |
| 정지 유지 | 정지 상태를 저장한 뒤 다음 날 실행 | 통과 |
| 자본 상한 | 상한 1%, 기존 보유 2%에서 실행 | 미통과 |
| 긴급 정지 | 별도 정지 명령이 있는지 확인 | 미통과 (없음) |

손실 정지는 BTC와 ETH를 전량 가상 매도하고 `halted=true`를 저장했다. 정지 유지 시험에서는 시세 조회가 호출되면 실패하도록 만들어 두고 다음 날 실행을 돌렸는데, 상태 파일과 원장이 바이트 단위로 그대로였다. 정확히 −5%인 950만 원에서 청산하면 수수료 4,250원을 빼고 9,495,750원이 남는 것까지 맞춰 봤다.

다만 이 장치의 한계도 같이 적었다. 하루 한 번 마감 가격으로 판단하기 때문에 실시간 감시가 아니고, 손실을 5% 안에서 막아 준다는 보장도 없다.

## 자본 상한이 초과 보유를 줄이지 못했다

문제는 자본 상한이었다. 가상 총자산 1,000만 원에 BTC와 ETH를 10만 원씩, 합쳐서 2%를 들고 있는 상태에서 상한을 1%로 걸었다. 목표는 종목마다 5만 원이니 각각 5만 원어치를 팔아야 한다.

그런데 주문이 하나도 나가지 않았다. 상한은 목표 비중에 곱해지기만 하고, 그 뒤에 일반 리밸런스 밴드가 적용된다. 밴드는 총자산의 1%(10만 원)보다 작은 차액의 주문을 생략하는데, 매도해야 할 5만 원이 거기에 걸렸다. 결국 20만 원이 그대로 남았다. 같은 계산이면 현금에서 1%로 시작할 때도 종목별 목표 0.5%가 밴드보다 작아 매수가 생략된다.

정리하면 그때의 상한은 목표 비중을 줄이는 장치였고, 넘친 보유를 반드시 줄이는 한도가 아니었다. 실거래를 시작할 때 총자산의 1%로 시작하기로 정해 뒀으니, 바로 그 규모에서 상한이 동작하지 않는 셈이었다. 이 상황을 그대로 재현하는 테스트를 먼저 만들었다. 이름은 `테스트_1퍼센트상한_기존밴드로_초과보유유지_재현`이고, 이 테스트의 통과는 문제를 재현했다는 뜻이다.

## 9월 24일 수정

자본 상한은 두 경우에 밴드를 적용하지 않게 바꿨다. 상한이 밴드 이하이거나, 현재 투자금이 이미 상한을 넘었을 때다. 상한을 넘은 상태에서는 신규 매수를 보류하고 기존 보유부터 줄인다. 최소 주문 금액이나 수량 단위 때문에 끝내 줄이지 못하면 정상 완료로 표시하지 않고 `halted=true`를 저장한 뒤 오류 코드 1로 끝낸다. 수정 후에는 1% 상한으로 현금에서 약 10만 원 진입, 2% 보유에서 1%로 축소, 줄일 수 없을 때 정지를 각각 시험했다.

긴급 정지는 파일 하나로 만들었다.

```bash
uv run python -m runner.kill_switch --strategy trend --engage
```

이 명령은 `state/trend/STOP` 파일을 만든다. 실행기는 시세를 조회하기 전과 주문 하나하나를 내기 직전에 이 파일을 확인한다. 실행 도중에 정지되면 이미 끝난 체결만 원장과 상태에 기록하고 `halted=true`, 오류 코드 1로 끝난다. 매일 실행 여부를 감시하는 watchdog도 그날은 정상 보고 대신 경고를 낸다.

이 긴급 정지가 못 하는 일도 문서에 남겼다. 이미 제출한 주문을 취소하지 않고, 보유 코인을 자동으로 팔지 않고, Mac이 꺼져 있으면 원격으로 멈출 수 없다. 텔레그램 봇은 보내기만 한다.

## 강제 발동은 격리된 곳에서

실제 운영 상태 폴더에서는 아무것도 터뜨리지 않았다. 임시 상태 디렉터리를 따로 만들고, 실제 명령 진입점 `kill_switch.main()`을 발동한 다음 실행기와 watchdog를 이어서 호출했다. 정지 파일 생성, 시세 조회와 주문 차단(오류 코드 1), 운영 경고까지 순서대로 확인했고 원장은 생기지 않았다. 실제 `state/trend/`는 읽기만 해서 그날 실행 기록이 정상이고 STOP과 halted가 없다는 것만 확인했다. 전체 테스트는 166개가 통과했다.

## 판정을 한 번 정정했다

처음에는 긴급 정지까지 붙인 뒤에도 G5를 보류했다. 사고가 나면 정지가 자동으로 걸리는지, 실주문 경로가 검토됐는지까지 봐야 한다고 생각했다. 그런데 미리 적어 둔 관문 문서를 다시 읽어 보니 G5는 세 장치를 각각 강제로 발동시켜 보는 시험이었다. 실주문의 거부나 부분 체결은 소액 실전에서 확인할 항목으로 따로 빼 뒀고, 실주문 경로의 사람 검토는 G6이었다. 그래서 같은 날 G5를 충족으로 고치고, 이 통과가 실전 주문의 안전성을 입증하지는 않는다는 문장을 붙였다.

실거래는 아직 보류다. 28일 연속 운영 관찰이 진행 중이고, 실주문 경로의 사람 검토(G6)와 실거래를 멈추고 모의거래로 돌아가는 절차의 검증(G8)이 남아 있다.
